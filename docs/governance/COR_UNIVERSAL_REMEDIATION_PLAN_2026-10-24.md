## 4. Remediation workstreams and ordered implementation

### P0 — Freeze candidate and evidence rules

**Objective:** one reproducible candidate, no stale results and no self-referential manifest fields.

1. Keep the protected branch unchanged while remediation is developed on a dedicated branch.
2. Every implementation commit becomes a candidate; run required suites against the exact candidate.
3. The evidence-only descendant mechanism may update evidence artifacts only. It must reject source, workflow, test, policy and configuration changes.
4. Remove `releaseHeadSha` from the manifest generator. Record `candidateSha` and compute the final release HEAD live in the verifier. Do not write a commit's own SHA into its own tree.
5. A candidate is rejected if any required suite is missing, any digest differs, any result has a different candidate SHA, or `unproven` is non-empty.

Example intended evidence rule (adapt to the repository's existing manifest schema rather than adding a competing schema):

```json
{
  "candidateSha": "<40-hex SHA of tested source candidate>",
  "allTestCommandsPassed": true,
  "unproven": [],
  "evidenceFiles": [
    { "path": "docs/security/evidence/live_ai_canary_receipt.json", "sha256": "<computed digest>" },
    { "path": "docs/governance/evidence/native-runner-evidence.json", "sha256": "<computed digest>" }
  ]
}
```

The values above are schema examples, not actual evidence. Never commit placeholder digests as a passing manifest.

### P1 — Implement a real per-model AI qualification lifecycle

**Objective:** fully wire Ugondu to the provisioned scalable `ai.airroofers.eu` API. No provider-specific secret, model ID or model inventory should be hardcoded in runtime logic.

#### Required lifecycle

```text
DISCOVERED
  -> SCHEMA_VALIDATED
  -> POLICY_CHECKED
  -> CAPABILITY_PROBED
  -> INFERENCE_VERIFIED
  -> QUALIFIED
  -> ACTIVE
  -> DEGRADED | DISABLED | RETIRED
```

Transitions must be persisted, auditable, idempotent and guarded by explicit transition rules. A model may not jump directly from DISCOVERED to ACTIVE. A failure transitions to a non-active state with reason code, timestamp, correlation ID and redacted provider response metadata. Never store credentials or full sensitive prompts in qualification receipts.

#### Contract and runtime rules

- Base URL comes from validated environment/configuration, with production default prohibited in tests unless explicitly supplied by deployment configuration. The production deployment is expected to use `https://ai.airroofers.eu`.
- Credentials are supplied by a secret manager or CI secret; never committed, logged, placed in evidence, or sent to an untrusted endpoint.
- Discover models through the API's documented model-list contract; validate the returned schema and preserve provider-issued model identifiers exactly.
- Read provider capabilities from the API response/contract. Do not infer support for tools, streaming, JSON mode, vision, context length or modalities from a model name.
- Run a safe capability probe and a real minimal inference for every model that is eligible for activation. Use model-appropriate tests only where the API contract exposes the capability.
- Persist model/provider ID, API contract version, qualification timestamp, tested candidate SHA, test suite version, latency, status code, correlation ID, result digest, policy decision and lifecycle state.
- Use bounded concurrency, retry only transient errors with jitter, respect rate limits, implement circuit breaking and never retry non-idempotent operations blindly.
- Activation is a policy decision, not merely successful HTTP. Apply region, data classification, capability, cost and safety policies before exposing a model to production routing.
- Keep Ugondu's deterministic execution engine operational when AI is unavailable. AI may assist planning, diagnosis or generation, but must not bypass policy, authorization, state transitions or evidence requirements.
- New future catalog models should be discovered automatically. They remain non-active until qualification succeeds; onboarding a new model must not require a code release solely to add its name.

#### Proposed types (implementation target, not a claim that these types exist today)

```ts
export type ModelQualificationState =
  | "DISCOVERED"
  | "SCHEMA_VALIDATED"
  | "POLICY_CHECKED"
  | "CAPABILITY_PROBED"
  | "INFERENCE_VERIFIED"
  | "QUALIFIED"
  | "ACTIVE"
  | "DEGRADED"
  | "DISABLED"
  | "RETIRED";

export interface ModelQualificationReceipt {
  providerId: string;
  modelId: string;
  state: ModelQualificationState;
  candidateSha: string;
  apiContractVersion: string;
  qualifiedAt: string | null;
  correlationId: string;
  checks: Array<{
    checkId: string;
    status: "PASS" | "FAIL" | "SKIP";
    reasonCode?: string;
    durationMs?: number;
    resultDigest?: string;
  }>;
}
```

#### Minimum acceptance criteria for AI

- Authenticated discovery is successful and validates the actual response schema.
- Every discovered model has an explicit disposition: qualified/active, policy-blocked, unsupported capability, provider error, or pending. No silent omissions.
- Every model marked ACTIVE has a recent real inference receipt bound to the candidate SHA and provider/model ID.
- A deliberately invalid credential fails closed and leaks no secret.
- Timeout, 401/403, 429, 5xx, malformed response and empty catalog are tested.
- A model failing qualification is never routed as active; a healthy qualified model can still be selected according to policy.
- Catalog growth works without source edits; unknown fields are handled safely and schema changes are visible.
- AI outage does not corrupt or block deterministic task-state recovery.
- CI canary does not run on untrusted fork pull requests and uses least-privilege token permissions.

### P2 — Zero-hardcoding, zero-stub and no partial implementation enforcement

A repository-wide validator passing is useful but not enough to prove the absence of semantic hardcoding. Implement a layered policy:

1. **Runtime data/configuration:** provider names, model IDs, model capability lists, endpoint URLs, locale strings, platform targets, IDE versions and host-specific parameters must be registry/configuration data, not scattered conditional branches.
2. **Legitimate constants:** protocol field names, cryptographic algorithms, invariant state names and security allow-lists may be constants when they are security controls. Each exception must have an owner, rationale, test and governance record. “Zero hardcoding” must not weaken security by making trust roots dynamically untrusted.
3. **Localization:** all user-visible strings resolve through locale catalogs. CI must fail on missing keys and user-facing literal strings in UI/CLI code, with narrow reviewed exceptions for diagnostics and protocol values.
4. **Mocks and stubs:** production dependency injection must not resolve test doubles. Test-only fixtures must be physically or import-boundary isolated. Production code must not contain fake successful adapters, canned provider responses, in-memory fallbacks masquerading as durable storage, or TODO-based success paths.
5. **Scaffolding:** generators may exist as developer tooling, but no generated placeholder implementation can be shipped as a working capability. A feature is either implemented and tested, or explicitly marked unsupported and unavailable.
6. **Partial implementations:** every capability registry entry must resolve to a real adapter, contract, tests, operations guide and evidence; otherwise its lifecycle status is experimental/disabled, not certified.
7. **Anti-regression:** run AST/static scanners, dependency-boundary checks, coverage checks, contract tests and adversarial mutation tests on every PR.

### P3 — Native OS, architecture and IDE qualification

Create a capability matrix driven by the supported-platform registry. Every declared target needs its own evidence row; cross-compilation proves compilation only, not native execution.

**OS/architecture targets to inventory:** Windows x86_64 and ARM64; macOS x86_64 and ARM64; Linux x86_64 and ARM64. Add any other target only if the product claims support for it. For each target, test clean install, first run, auth, core workflow, upgrade, interrupted upgrade recovery, rollback, uninstall/cleanup, permissions, filesystem paths, proxy/TLS behavior and artifact signature.

**IDE targets:** VS Code, JetBrains family members explicitly listed in the registry, Cursor, Windsurf and Neovim. For each version range: install, connect to Ugondu, authenticate, discover capabilities, run a real task, display actionable failure, update and uninstall. An IDE is not certified merely because a generic extension package builds.

**Runner rules:**
- Prefer native GitHub-hosted runners where available or controlled self-hosted runners with documented hardware, image, patch level and isolation.
- Every receipt includes OS name/version, architecture, runtime versions, runner identity class, candidate SHA, artifact digest, command exit codes and timestamps.
- Separate `BUILD_ONLY`, `CROSS_COMPILE_ONLY` and `NATIVE_EXECUTION` evidence states. Only `NATIVE_EXECUTION` can satisfy native certification.
- Do not use a Go thin-client pass to claim the full macOS product is certified.

### P4 — Host/provider adapters and real operation receipts

Each adapter must implement the same operation contract and emit durable receipts for **plan → preflight → mutate → verify → rollback (when required) → cleanup**.

Required provider receipt fields:

```json
{
  "executionId": "<unique execution id>",
  "candidateSha": "<tested source SHA>",
  "provider": "<registry provider id>",
  "operation": "provision",
  "targetFingerprint": "<non-secret target identity>",
  "startedAt": "<RFC3339 timestamp>",
  "finishedAt": "<RFC3339 timestamp>",
  "result": "PASS",
  "verification": { "status": "PASS", "checks": [] },
  "rollback": { "attempted": false, "result": "NOT_REQUIRED" },
  "cleanup": { "status": "PASS" },
  "evidenceDigest": "<SHA-256>"
}
```

This is a format illustration, not a real receipt. Receipts must be generated from actual adapter execution; never fabricate values to make a matrix green.

Provider-specific acceptance:
- **AWS:** OIDC-based least privilege; region required; resource tags and transaction IDs; real describe/read-after-write checks; cleanup verified. Destructive actions require an explicit policy gate.
- **cPanel/DirectAdmin:** shared-host-safe deployment; no root/sudo assumption; verify PHP/runtime/filesystem/permissions and available deployment mechanisms before mutation.
- **SSH/VPS:** host-key verification, scoped credentials, idempotent remote command plan, bounded timeout, atomic release directory/symlink swap where supported, rollback receipt.
- **Docker:** real build from locked inputs, image digest, container health check, persisted data test, stop/remove cleanup.
- **Kubernetes:** disposable namespace/cluster or dedicated test environment, rollout/readiness checks, rollback, namespace/resource cleanup and audit evidence.
- **GCP/Azure:** do not expose as certified until real provider credentials, adapter tests, operation receipts and rollback are complete.

### P5 — Release publication and provenance

1. Test tag protection and release workflow on a disposable test tag/repository or non-production channel.
2. Verify the tag points to the intended candidate and the workflow checks out the exact tag SHA.
3. Build artifacts from locked dependencies; record artifact hashes and build provenance.
4. Sign release metadata using the configured signing authority; verify signatures independently.
5. Confirm the release contains only intended artifacts, SBOM, checksums, notices and installation/rollback instructions.
6. Verify retry, failed publish, partial upload, revoked tag, compromised credential response and cleanup.
7. Do not publish production releases if any universal certification row remains open when the release is advertised as universal.

## 5. Real E2E strategy (no mock-only certification)

A test counts as real E2E only if it crosses the actual process/service boundary and verifies observable side effects. Unit tests with mocks remain useful but cannot satisfy deployment/provider certification.

| Scenario | Real operation | Required assertion |
|---|---|---|
| AI discovery and inference | Authenticated request to `ai.airroofers.eu` | Real response, provider/model identity, latency, correlation ID and redacted receipt. |
| Model qualification | Each discovered eligible model | Every ACTIVE model has successful candidate-bound qualification. |
| Deployment | Disposable real target for each provider | Resource/state actually changes and is independently read back. |
| Rollback | Inject failure after mutation | Original state restored; receipt proves before/after fingerprints. |
| Resume | Interrupt a multi-step task after persisted checkpoint | Restart resumes from durable state without duplicate side effects. |
| Auth negative tests | Invalid/expired/wrong-scope credentials | Fail closed, no privilege escalation, no secret leakage. |
| Network failure | DNS, timeout, 429 and 5xx injection at transport boundary | Bounded retry/circuit behavior; durable state remains consistent. |
| Cleanup | Successful and failed executions | Temporary resources removed or residuals reported as blocker. |
| Release | Signed candidate tag | Exact source SHA, provenance, hashes, signature and release assets agree. |

Use disposable accounts, projects, clusters and test hosts. Do not use destructive production operations as a test fixture. Preserve logs with secrets and personal data redacted.

## 6. Evidence schema and anti-regression policy

Each receipt must contain at minimum:
- schema version and evidence type;
- candidate SHA and repository identity;
- execution ID, start/end timestamps and runner environment;
- exact commands and exit codes;
- target/provider/model IDs as applicable;
- artifact/configuration digests;
- pass/fail/skip status with reason codes;
- links or paths to raw logs and sanitized reports;
- signature or integrity digest where required.

Rules:
- `SKIP`, missing evidence, expired evidence, mismatched SHA, digest mismatch or unknown status are **not PASS**.
- Evidence must be generated by the gate, not hand-authored to represent a test result.
- Every release run should create an immutable candidate-indexed evidence directory and a machine-readable summary.
- Any source, workflow, policy, lockfile or test change invalidates dependent evidence and requires relevant gates to rerun.
- A regression from PASS to FAIL/UNKNOWN turns the overall certification red/orange and blocks release.
- Keep historical snapshots to make regression visible; do not overwrite old evidence without preserving provenance.

## 7. COR / UAIGOS governance mapping

| Governance principle | Enforcement expected |
|---|---|
| Deterministic lifecycle | State machine with explicit transitions, persisted checkpoints, idempotency and replay tests. |
| Evidence-based compliance | Every claim maps to machine-generated evidence and a verifiable digest. |
| Fail-closed release | Missing secrets, missing region, stale evidence, unknown target or absent rollback proof blocks certification. |
| Separation of kernel and extensible adapters | Core contracts remain stable; provider/IDE/host adapters implement versioned contracts. |
| No hardcoded product/provider inventory | Registries and manifests drive runtime resolution; reviewed invariant constants remain controlled. |
| No fake completeness | Unsupported/experimental capability is not exposed as certified or active. |
| Least privilege | CI permissions and runtime credentials scoped to the exact operation and target. |
| Reproducibility | Locked dependencies, exact SHA, recorded environment, artifact hashes and deterministic evidence generation. |
| Independent finalization | COR finalizer revalidates the candidate and evidence bundle; signature is separate from test execution. |
| Universal claims are bounded by evidence | Certification only covers the exact OS/architecture/IDE/provider/version combinations tested. |

The repository contains COR workflows and governance artifacts, but their presence alone does not establish that every policy is satisfied. The current evidence still has open universal-support rows.

## 9. Definition of done and release decision

Universal certification may turn green only when all of the following are true:

- All required contract, security, integration, localization, governance and release gates pass on one exact candidate.
- AI discovery accounts for every model; every ACTIVE model has real current qualification evidence and all other models have explicit non-active disposition.
- All claimed OS/architecture/IDE/host combinations have native or provider-real E2E evidence at the declared support level.
- Provisioning, verification, rollback and cleanup are proven for every adapter claimed certified.
- No production mocks, stubs, fake success paths or placeholder implementations remain; any unsupported capability is disabled and accurately declared.
- User-facing strings and runtime provider/platform inventories are externalized into governed catalogs/registries, with narrow documented invariant exceptions.
- Manifest digests and candidate binding verify; no stale or unproven evidence exists.
- Tag-gated release publication and provenance have been tested.
- Independent COR finalization succeeds and its signed evidence bundle is retained.
- No mandatory dashboard row is 🟡, 🟠, 🔴 or ⚪.

**Until then, the release must remain “QUALIFIED WITH BOUNDED TARGET SUPPORT”; do not label it universally certified.**
